## 一、计划目标与约束

### 1.1 目标

在不推翻项目原有阵型设定的前提下，形成一个可被自动结算、白刃标准模式和六角微操共同消费的阵型规则核心：

1. 以本项目既有六基础阵型、武将阵型精通、兵种适配、地形、组织度和五部阵位为主体。
2. 吸收抽象维度 A“阵型是持续战斗姿态”的决策感，以及抽象维度 B“阵型首先改变部队空间展开”的直观性。
3. 保持战争四层结构不变：行政大地图 → 郡域战场 → 局部交战 → 单挑。
4. 保持局部交战三种入口不变：自动结算 / 标准模式 / 六角微操。三者读取同一权威快照，并最终只进行一次幂等回写。
5. 建立原创、可解释、可测试、可迁移的实现边界，清理当前静态目录、精通数据和运行时配置之间的漂移。

### 1.2 非目标

本计划不做以下事项：

- 不把两款参考作品的规则、数值、界面或资源逐项复刻。
- 不新增并列大系统、第五层战争结构或第四套伤害引擎。
- 不新增 `formationIntegrity`、`wingPressure`、`centerPressure` 等持久字段。
- 不新增独立“合围”战术点命令，也不改变“整顿”的原有效果。
- 不在本轮扩充 0-B 的 27 阵、9 水阵、阵型双轴成长、科技树或“极”效果。
- 不把参考作品中的阵型名称排列、坐标、美术构图、文本或隐藏数值当作可直接复制的生产资产。

### 1.3 文档权威顺序

发生冲突时按下列顺序处理；低位文档不得静默覆盖高位真源：

| 2 | `08-data-dictionary.md` | 静态数据规模、稳定 ID 与数量真源 |

## 三、前期调研阶段

### 3.1 调研原则

调研目标是抽取抽象设计规律，不是逆向取得可复制内容。证据按以下等级记录：

| 等级 | 证据 | 可用于 |
|:--:|------|--------|
| A | 官方说明书、发行方页面、合法公开的开发者说明 | 确认阵型种类、操作流程、显式规则 |
| B | 多个相互印证的公开攻略/实机记录 | 建立待验证假设，不直接进入生产数值 |
| C | 单一社区表、记忆描述或来源链不完整的转述 | 只列风险和待验证项，不作为实现依据 |
| 排除 | 声称来自 ROM、反汇编、内存读取或资源提取的数据 | 不访问、不保存、不引用，也不进入证据台账正文 |

所有调研条目写入证据台账，记录来源 URL、访问日期、证据等级、可借鉴的抽象理念、禁止复制的表达以及本项目原创转化方式。

### 3.2 抽象维度 A阵型系统分析

官方说明书概览可确认“武将分别设定阵形”是战场核心之一；下列 12 类目录与地形分类是本轮
公开资料交叉核验所得的**调研基线**，仍须在 W1 证据矩阵中逐项标注 A/B 级来源。当前 A 级
证据尚未确认一张可移植的固定“阵型互克倍率表”；本项目据自身原设定决定不建立此表，
而把武将掌握范围、地形、移动、方向与持续姿态作为组合判断：

| 维度 | 调研对象 | 本项目如何理解 |
|------|----------|----------------|
| 阵法种类 | 12 类阵型：鱼鳞、锋矢、鹤翼、偃月、方圆、雁行、长蛇、衡轭、箕形、钩行、锥行、水阵 | 仅用于识别“不同阵型承担不同战术角色”的设计理念；本轮仍以本项目六基础为准 |
| 阵型效果 | 攻守、机动、射击、方向防护等多维差异 | 继续承载到本项目既有攻/防/机/射和特殊效果，不复制原作数值 |
| 适用场景 | 平地、山地、水域、攻守态势及受击方向影响表现 | 复用本项目 `terrainModifiers`、兵种限制和朝向规则 |
| 武将约束 | 武将只会部分阵型，阵型选择与人物能力绑定 | 复用 `formationMastery`；AI 与玩家同一合法性校验 |
| 交互 | 开战选阵、战中维持姿态；改变阵势是有代价的决策 | 战役阵型继承入场；标准模式变阵保持 1 TP 且推进一个白刃回合 |
| 数值观 | 当前证据支持继续核验多维属性、地形与方向，未确认可移植的阵型互克倍率 | 项目设计决定禁止新建六阵互克矩阵；只保留已有战术—阵型协同区和兵种克制 |

调研阶段需输出 `san5-formation-evidence-matrix.md`，逐项区分“官方明示”“社区推测”和“本项目原创”。官方手册或社区表中的精确数值均不直接抄入实现。

### 3.3 抽象维度 B阵型系统分析

合法取得的说明书正文与公开文字记录可用于核验“开战前可选阵形”这一功能事实。
长列、翼展、楔入、鳞列四类只是多人 clean-room 研究路径的**检索工作标签**，
不是对原作阵型名称、数量、坐标或视觉布局的生产结论；单人独立实现路径跳过视觉布局归类。
本项目的五部部署只从自有先锋/中军/左翼/右翼/后卫语义独立设计，可借鉴的抽象价值仅是
“阵型优劣可通过单位位置和接敌顺序显现”，而不是一套可移植的百分比 Buff 表。

| 维度 | 调研对象 | 本项目如何理解 |
|------|----------|----------------|
| 阵法种类 | 多人研究路径待 W1 复核的四个检索标签：长列、翼展、楔入、鳞列 | 不复制其名称组合或坐标；实现仅提炼“空间展开产生规则”的抽象思路 |
| 阵型效果 | 改变前后排、翼侧宽度、主将暴露度与首次接敌次序 | 映射到既有先锋/中军/左翼/右翼/后卫五部阵位 |
| 适用场景 | 进入局部战斗前选择，随后由单位移动与接敌兑现 | 战役阵型生成原创初始部署，六角模式可视化，自动/标准模式读取同一派生结果 |
| 数值体系 | 公开一手材料不足以支持“固定加成比例/互克倍率”的移植结论 | 不创造“原作百分比”；只验证空间派生是否改变合法位置和接敌关系 |
| 资源消耗 | 当前 A 级证据只确认开战可选阵形，尚不足以否定所有隐藏/持续成本 | 项目设计决定不新增资源；继续使用既有战术点和回合成本 |
| 交互 | 选阵 → 生成起始阵位 → 单位行动 | 融入既有入口，不增加新的战斗层或单独布阵小游戏 |

调研阶段需输出 `haou-deployment-evidence-matrix.md`。多人路径中，仅研究者可在合法取得的材料中
核验功能事实；不得向实现者传递页面、截图、坐标、构图或可还原的布局描述。单人路径只使用文字功能事实，
不以原作视觉布局推导部署。任何路径下，原作页面、截图、原文、坐标和图形均不得进入代码库、产品或宣传物料。

## 四、设计融合阶段

### 4.1 融合原则

本项目原设定是主体，参考作品只提供两个互补视角：

```text
抽象维度 A：阵型 = 持续姿态 + 地形/方向/武将约束
抽象维度 B：阵型 = 可见的初始空间展开
                         ↓
本项目原创融合：稳定阵型 ID + 五部部署模板 + 同源规则解释
```

### 4.2 六基础阵型的原设定角色

以下只定义角色和体验目标；具体点值仍来自 `05 §4.5`，当前运行百分比仍以 `27 §6.2` 为回归基线，二者在数值门禁通过前不得混算。

| 阵型 | 核心角色 | 优势场景 | 明确代价 | 五部空间表达 |
|------|----------|----------|----------|--------------|
| 方阵 | 均衡、维持战线 | 情报不足、混合兵种、稳步接敌 | 爆发和追击不突出 | 中军居中，四部紧密、左右对称 |
| 圆阵 | 防守、护卫中军 | 守点、承受突击、保护低兵力部 | 机动和先手弱 | 先锋后收，翼侧与后卫环护中军 |
| 锥形 | 突破、抢先接敌 | 平地突进、骑兵或枪兵锋面 | 侧翼薄弱 | 先锋最前，中军随后，两翼斜后展开 |
| 雁行 | 远程展开、纵深火力 | 弓弩和开阔视野 | 近身后阵线脆 | 左右翼拉开，中军与后卫形成射击纵深 |
| 鹤翼 | 翼侧包抄 | 有足够左右翼、可形成夹击 | 中军受奇袭风险较高 | 两翼前伸且拉宽，中军相对后置 |
| 锋矢 | 中央强突、快速决胜 | 集中强将和骑兵突破 | 防御与持久战弱 | 先锋与中军成矢尖，两翼贴近，后卫拉后 |

冲阵 ID 16 保持“仅骑兵的高阶/特殊阵型”定位。0-A 保留其静态数据和特定武将精通，
但 FM-P0～P5 不把它加入战役初选、标准变阵或六角变阵候选，也不建立独立命令/入口。
以后若经用户另行批准启用，仍必须复用同一选择器、合法性解析器和对应模式已批准的 1 TP/阶段消耗语义，
不得借“特殊阵型”另造资源或绕过科技树边界。

### 4.3 原创五部部署模板

部署不新增持久状态，而是在进入局部交战时由阵型 ID 和现有 `CampaignSquad.position` 派生：

```ts
type SquadPosition = 'vanguard' | 'center' | 'left' | 'right' | 'rearguard';

interface FormationDeployment {
  slots: Partial<Record<SquadPosition, HexOffset>>;
  fallbackOrder: readonly SquadPosition[];
  symmetry: 'symmetric' | 'left_weighted' | 'right_weighted';
}
```

约束如下：

- 偏移坐标必须由本项目原创，不抄录参考作品站位。
- 同一方已存在的 Squad 只能占一个位置；缺部时按 `fallbackOrder` 收缩，不能生成虚构部队。
- 主将仍在中军；参谋不占阵位；五部含义沿用 `05 §13.3`。
- 自动、标准和六角模式用同一个部署解析结果。自动模式把位置关系折算为既有编成项；六角模式将其投影为初始格。
- “夹击/包抄”由左右翼、六角邻接和朝向派生，不新增“合围 3 TP”命令。

### 4.4 组织度复用

“阵势是否完整”只作为 UI 解释语，不新增字段。唯一权威数据仍为 `CampaignArmy.organization: 0..100`：

| 组织度 | 状态 | 既有阵型执行效果 |
|:--:|------|------------------|
| 80~100 | 严整 | 阵型加成 ×1.2，指令无延迟，溃逃概率 -50% |
| 60~79 | 有序 | 阵型加成正常 |
| 40~59 | 松散 | 阵型加成 ×0.8，士气衰减 +10% |
| 20~39 | 混乱 | 阵型加成 ×0.5，溃逃概率 +30% |
| 0~19 | 崩散 | 阵型加成归零，每回合 20% 概率溃逃 |

结算时严格区分两个语义：

1. 自动战斗现有 `orgCoeff` 表示军队全局战备状态。
2. 上表的档位乘数只作用于“阵型贡献的增量”，表示阵型执行力。

解释器必须分项显示，禁止把同一个组织度乘数对整条伤害链重复应用，或把阵型档位再次乘到已含组织度的全局项上。标准/六角模式若尚无全局 `orgCoeff`，只消费阵型执行项。

### 4.5 资源消耗与切换流程

原设定保持不变：

1. 战役层已选阵型继承到局部交战，不再赠送第二次免费覆盖。
2. 标准模式变阵固定消耗 **1 战术点**，提交后推进并结算一个白刃回合。
   六角模式同样消耗 1 TP 且每回合至多一次，只消耗 `battle.ts` 自身的主将行动，不调用
   `runMeleeRound` 或结算白刃回合；状态机已冻结为玩家阶段、主将未行动时可用。
   “布划”的百分比成本缩减不得折算为 0 TP。
3. 每回合基础获得 5 战术点；主将智力 ≥80 追加 1；上限 10。
4. “整顿”目标语义仍为 2 TP、士气 +10、疲劳 -15；当前引擎遗漏疲劳写回，列入 FM-P3
   原设定清债，不得改为恢复新字段。
5. 变阵需同时通过武将精通、兵种、地形、特殊条件、当前阶段、未被围和“本回合尚未变阵”
   校验；本切片六阵没有被围例外。非法操作必须原子拒绝且不消费 RNG。
6. 六角模式沿用同一服务端合法性、1 TP 和每回合一次门禁；服务端在玩家阶段检查主将未行动，
   成功后同步攻方存活 BattleUnit 阵型并结束主将行动。客户端不能自定规则或只靠按钮禁用，
   也不能借道白刃回合引擎。

`布阵` 与 `布划` 的原职责在实施前冻结：

- 通用技能 `布阵 / formationChange`：保留切阵后首回合反击联动。
- 战略特性 `布划`：成本缩减只作用于长期“战略层 1 回合调整阵位”语义，本切片继续后置；
  切换后的连击/反击联动可在 Gate N1 后接入，但不改变 1 TP。
- 两者目前均未完整接入运行态；FM-P0 先形成职责测试表，再实现，不得把两个名称或效果混为一项。

### 4.6 既有战术与克制关系

- 保留 `27 §6.3` 的强攻、固守、奇袭三战术及协同区 `1.1 / 0.9 / 1.0`。

- 兵种克制继续由既有 `getUnitMatchup` 规则处理。
- 最佳兵种继续使用 `08` 规定的额外 **+10%**，不改为其他比例。
- 六角侧击继续使用现有武器差异：剑 +12%、矛 +8%、斧 +18%；背后目标当前不可直接攻击。本计划不新增通用背击倍率。

v1 文件和 Schema 保留为只读兼容/迁移测试夹具，禁止直接改变其形状后仍称 schemaVersion 1。

## 五、数值体系与结算权威

### 5.1 当前两种量纲不得直接叠加

当前文档存在两个用途不同的数值层：

- `05 §4.5`：长期目标的 Lv1~Lv5 攻/防/机/射“点值”及特殊效果。
- `27 §6.2` / `meleeRound.ts`：Session 277 白刃标准模式的 0-A 百分比运行切片（回归基线）。

**N1 已审：唯一运行量纲 = `tiers[0]` 点值 + `effects` 暴击链。** **Session 291** 已把标准模式
`runMeleeRound` 迁移到点值消费（等价性单点换算 `MELEE_ATK/DEF_GAIN=0.1`、`MOB_GAIN=0.5`、
`MOB_BASE=1.0` + 组织度执行档），`meleePercent` 过渡字段退役；`27 §6.2` 百分比仅保留为回归基线
登记（逐阵差异见 `formation-catalog-migration.md` §4.2 迁移对比，诚实标注不逐点相等）。

本计划不批准第三套数值，也不允许把点值和百分比同时加到伤害链。FM-P0 的数值门禁 N1 必须产出一张逐阵型映射表，包含：

| 字段 | 要求 |
|------|------|
| 设计点值 | 原样引用 `05 §4.5` 的 Lv1 数据 |
| 当前百分比 | 原样记录 Session 277 的回归基线 |
| 目标标准化输出 | 明确攻、防、机、射及暴击率/反击率/反击系数/连击率的唯一运行量纲 |
| 换算理由 | 说明是线性换算、查表还是模式专用投影 |
| 影响引擎 | 自动 / 标准 / 六角分别列出消费位置 |
| 回归样例 | 给出相同输入在迁移前后的可解释差异 |
| 审批状态 | 设计、程序、测试与用户审核 |

N1 未批准前不得替换现有数值常量。

### 5.2 唯一计算顺序

共享阵型解析器只生成“阵型贡献”，不计算最终伤害：

```text
目录与精通合法性
  → 取当前阵型等级（0-A 固定 Lv1）
  → 兵种允许/最佳兵种 +10%
  → 地形与特殊条件
  → 组织度档位只缩放阵型增量
  → 战术协同区（标准模式需要时）
  → 五部/六角位置派生
  → 输出 modifiers + deployment + explanation
```

Gate N1 必须把每个标准化维度写成下列分项伪式，不能只写“依次相乘”：

```text
F_raw = 阵型 Lv1 映射 + 阵型地形项 + bestUnits 项 + 阵型特殊项
F_effective = F_raw >= 0 ? F_raw × organizationExecution : F_raw
T_base = 战术自身的基础修正                         # 不受组织度缩放
resolvedDelta = (F_effective + T_base) × synergy    # 1.1 / 0.9 / 1.0
```

负阵型修正必须原值保留：崩散会清零正面阵型收益，但不能顺便消除圆阵攻击弱点或锥形防御弱点；
严整也只增强正面贡献，不放大负面。暴击/反击/连击等阵型贡献遵守同一正负规则，最终事件概率仍由
既有 `crit.ts` 结算。

位置侧击按模式互斥，禁止双算：

| 结算模式 | 位置规则 |
|----------|----------|
| `runAutoBattle`（含目标局部自动入口） | 只使用 `05 §13.3` 五部侧击 +10% |
| `runMeleeRound` 标准模式 | 当前没有六角朝向，不叠加武器侧击；若未来加入五部项须另过 N1 |
| 六角 `battle.ts` | 只使用剑/矛/斧 +12%/+8%/+18% 的实际朝向侧击，不再叠五部 +10% |

五部身份只决定六角初始部署，不让同一次命中同时获得“五部侧击”和“武器侧击”。

战役层 `runAutoBattle`、白刃 `runMeleeRound` 和六角 `battle.ts` 作为三套既有权威引擎，只消费
上述输出。**Session 290** 已将局部“自动结算”从 `game.ts` 的 `runMeleeRound(normal_attack)` 漂移恢复为
调用既有 `runAutoBattle`，并完成 RNG、战果和单次 Army 回写回归。这里是重接既有引擎，不是新增第四套公式。

## 七、技术实现路径

### 7.1 目标数据模型

实施时迁移到 `03-data-models.md §9` 已定义的 `Formation`，不建立并行 V2 类型。允许的原创扩展仅为可选部署字段：

```ts
interface Formation {
  // 既有长期目标字段：id/name/family/tiers/ultimate/effects/
  // allowedUnits/bestUnits/restrictedUnits/terrainModifiers/prerequisites/specialUnlock
  deployment?: FormationDeployment;
}
```

0-A 投影策略固定如下，避免“迁到长期类型”等同于提前开放成长：

1. 7 条记录都满足长期 `Formation` 必填结构，补齐 `family/tiers/ultimate/prerequisites`；这些是内容
   完整性数据，不代表相应玩法已开启。
2. 运行态通过版本化 `ZERO_A_PLAYABLE_FORMATION_IDS = [0,1,2,3,4,6]` 只消费六阵 Lv1；
   Lv2~Lv5、`ultimate`、熟练度和科技树全部 dormant，UI 无升级入口。
3. 0-A 的 prerequisite 跨引用校验可接受指向稳定 `FormationType` 枚举但未载入本切片的 ID
   （如鹤翼前置长蛇 8、冲阵前置车悬 14），但只能登记为 `external-to-slice`，不得据此解锁。
   进入 0-B 全目录时恢复“目标记录必须存在”的严格跨引用校验。
4. 上述活跃 ID 列表是版本化规则范围，不含名称、属性或效果；不得演变成第二份阵型内容表。

TacticalConfig 另行从 v1 升为 v2，不属于平行 Formation 模型：v2 保留 grid/duel/tactics，
以 `formationIds: number[]` 表达战术关系，不再存阵型名称和攻防机动值；v1 Schema/JSON 保留为
兼容夹具，并提供显式 `v1 → v2` 迁移测试。

顺序固定为：

```text
Zod Schema 与共享 Type
  → Schema 单测与迁移夹具
  → formations.json
  → officers.json formationMastery
  → 加载器与跨引用校验
  → 引擎消费
  → API/UI
```

### 7.2 共享纯函数内核

```ts
getAvailableFormations(context): FormationAvailability[];
validateFormationChange(context, targetId): ValidationResult;
resolveFormationContribution(context): FormationResolution;
resolveFormationDeployment(context): DeploymentResolution;
explainFormationResolution(resolution): FormationBreakdown[];
```

`FormationResolution` 至少返回：稳定 ID、有效等级、攻防机射贡献、暴击率/反击率/反击系数/
连击率贡献、组织度执行系数、兵种/地形/战术命中项、五部部署、禁用理由和可本地化解释键。

### 7.4 三模式接入

| 战役层自动战斗/强攻 | `runAutoBattle` | **✅ Session 292 已接入**：`formationMod` 由 `autoFormationMods` 生成（攻防点值 ×0.1 合并战力修正 + 五部侧击 +10%，组织度执行档只缩放正面增量、负修正原值保留）；守城无 Army 时守方无阵型贡献（城墙惩罚表达守势） | 不改造成白刃逐回合伤害；`mobility/range` 点值不参与自动战力 |
| 局部“自动结算”入口 | ✅ Session 290 已复用 `runAutoBattle` | 从同一 Melee/Army 快照读取阵型贡献并一次结算 | 已完成：不再保留旧漂移，不另造自动伤害公式 |
| 标准模式 | `runMeleeRound` | **✅ Session 291 点值迁移 + Session 296 战术协同矩阵**：阵型贡献（`tiers[0]` 点值经等价性换算）+ 组织度执行档；战术姿态 `MeleeState.tactic?`（assault/hold/ambush，持久字段，白刃面板可设、不耗 TP）经 TacticalConfig v2 消费——T_base 修正 + synergy 对敌阵（克 1.1 / 中性 1.0，0-A 无 0.9 触发源）；1 TP 变阵合法性既有。战报解释 UI 仍后置（FM-P4） | 不增加第二次免费选阵 |
| 六角微操 | `battle.ts` 与战术阶段协议 | **✅ Session 295 阵型贡献 + Session 297 部署注入 + Session 301 变阵状态机 + Session 302/303 战报与浏览器链**：`hexFormationMods` 把 `tiers[0]` 点值按六角公式量纲投影（攻×2 进 baseAttack / 防×2.5 进 baseDefense，负原值保留，orderly 中性），`CampaignArmy.squads` 按 `projectHexDeployment` 生成多个 BattleUnit；普攻、战法、火计、AI 与灼烧按整方存活 unit 判定终局；变阵每回合一次、消耗 1 TP、主将未行动时生效并同步攻方存活部队；`BattleReport` 展示变阵/攻击结构化解释，浏览器链已实测 | 不在客户端自算结果；⏳ 存档/读档验收留后续 |

三种玩家入口不等于三套新伤害引擎。它们仍可能因操作粒度不同产生不同最终战果；“同源”
指同一输入下阵型合法性、属性贡献和解释一致，不要求自动、白刃与六角输出相同伤亡。

### 7.5 API、事务与 RNG

- 复用现有 `POST /api/game/melee/round` 路径，但 FM-P3 为变阵请求补充
  `{ actionType, targetFormation?, commandId, expectedRound }`。`commandId` 用于去重，
  `expectedRound` 用于乐观并发校验；对应 Zod/Type 与 `MeleeState` 有界去重记录必须先行。
- 同一 `commandId` + 同一请求体重试返回首次结果，不二次扣 TP/推进；同 ID 不同请求体拒绝。
  `expectedRound` 过期也原子拒绝。**Session 290 已实装**：`/melee/round` 接受这两个字段，
  `MeleeState.commandCache` 提供动作级幂等；战后 `settlementApplied` 仍负责结果回写幂等。
- 若六角模式需要变阵入口，优先接入既有战斗命令编排并采用同一 command/version 契约，
  不建立重复的“阵法服务”。
- **Session 301 已实装**：六角变阵使用 `POST /api/game/battle/formation`，请求 `{ unitId, targetFormation }`；
  服务端消费 `BattleState.tacticalPoints/tacticalPointsUsed` 与 `BattleUnit.hasActed`，成功后写入
  `actionHistory.kind=formation`，不改变白刃 `MeleeState.round`。
- 服务端按当前权威状态重新验证精通、兵种、地形、TP、阶段与目标 ID。
- 非法命令原子失败：状态、TP、回合、操作历史和 RNG 游标均不变化。
- 合法变阵一次事务完成扣 TP、写阵型、写去重记录、推进回合和日志。
- AI 调用同一个 `getAvailableFormations` 与 `validateFormationChange`，不得绕过精通或成本。

### 7.6 存档迁移

- 稳定 ID 0~26 不重用；7/8 仍代表偃月/长蛇。
- 对活动战斗、活动白刃、CampaignArmy 及武将精通分别制作迁移夹具。
- 旧存档若引用本轮目标目录以外的 7/8，不静默改成 1/3，也不一律落到 0；按版本化迁移表处理并记录 migration log。
- 当前 UI 可编成 ID 16，因此 Gate M 必须扫描 `CampaignArmy.formation`、活动 Melee/Battle 的
  在用冲阵。既有存档中的在用 16 不替换、不报废：标为“旧档兼容当前阵”，允许维持到玩家
  首次合法变阵或该 Army/交战结束，但不能在新候选中重新选择；其旧数值由版本化兼容解析器
  保持。新局与迁移后的新选择始终只开放六基础。
- 无法确定语义的存档必须给出可解释错误或进入显式兼容分支，不能让加载成功但阵型含义改变。

### 7.7 UI 与可访问性

- 六基础阵型卡始终全部展示；合法项可选，未精通/兵种/地形/被围/本回合已变阵等非法项禁用
  并显示稳定原因，不能一边隐藏非法项一边要求用户理解禁用原因。
- 五部预览必须同时使用形状、文字与阵位标签，不只靠颜色。
- 冲阵若在资料区展示，只能作为只读“高阶阵·本切片未开放”，不得进入战役初选、标准变阵或
  六角变阵候选；普通六基础仍按精通/兵种/地形显示可选或禁用原因。
- 战报显示“基础阵型 → 兵种 → 地形 → 组织度 → 战术 → 位置”的逐项解释。
- Konva `<Text>` 显式使用 `HanDynastySerif`，且 Stage 继续经过 `waitForGameFonts()` 屏障。
- 本轮不引入任何外部美术或音频资源。
