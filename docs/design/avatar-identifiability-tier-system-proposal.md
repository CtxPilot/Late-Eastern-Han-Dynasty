## 一、提案目的与边界

本提案记录一套未来可能用于增强武将头像辨识度的“三层区分体系”。它试图让玩家先从大轮廓和色彩识别阵营、再从头饰识别身份、最后从个人符号识别核心人物，从而在不要求所有头像都进行高成本精细绘制的前提下，提高扫视辨认效率。

本轮只保存候选方法论及未来启动前的检查清单，不确认配色、不确认参数、不评估现有实现，也不产生任何排期或代码任务。HC-P1（称王）和 CMD（人事域 UI 迁移）仍是当前工程线；本提案须排在两条工程线均收尾之后，再由用户决定是否启动审计。

## 二、方法论核心：三层区分体系

### 第一层：势力色

以头像的大面积、低频视觉区域表达势力归属，使玩家在最短时间内完成阵营识别。候选概念为：

- 魏：玄蓝
- 蜀：翠绿
- 吴：朱红
- 群：赭金

这些名称只是提案原始构想，**不是已批准色值或新色板**。启动前必须先完成下文“色板冲突排查”，确认能否与既有语义色规则共存。

### 第二层：身份型头饰

以稳定、可复用的头部轮廓表达人物身份，先设四类原型：

- 君主：冕、通天冠或能够形成最高权力轮廓的同类原型
- 武将：兜鍪、武冠、护额等军事身份原型
- 文官：进贤冠、梁冠等文官身份原型
- 特殊：方士、隐士、异族、女性等不能被前三类准确覆盖的身份原型

四类只定义识别层级，不在本提案中确定具体冠式、时代考据细节、SVG 结构或变体数量。

### 第三层：个人符号

对约 50 名核心武将进行全参数定制，使其在同势力、同身份原型内仍能通过轮廓、五官、髯须、体型、标志物等个人符号被识别。个人符号应服从项目既有“金石水墨·拓片简册·印信官职”美术基调，不以高保真写实或模仿知名商业三国游戏构图为目标。

“50 名”是本候选方案的分层设想，不在本轮修改任何数据规模真源，也不代表已经选定名单。

## 三、`GeneralVisualProfile` 接口设计草案

以下仅用于记录未来可能需要表达的参数维度。字段名、枚举、数据归属、默认值和与现有类型的合并方式均未拍板：

```ts
interface GeneralVisualProfile {

```

本草案不应直接新增为并行类型。未来若启动，必须先审计并复用、扩展或迁移现有 `ExpressionPortrait` / `OfficerPortrait` 参数体系。

## 四、次要武将的“模板 + seed 微变”策略

对约 173 名次要武将采用模板化生成：

1. 先按势力与身份原型选择基础模板。
2. 再以稳定 seed 对模板允许的参数做小幅、确定性变化，例如脸型子变体、眉眼组合、髯须、体型比例、服装细节和局部纹理。
3. 同一武将跨页面、跨存档和跨运行环境必须得到一致结果；seed 不得引入运行时随机漂移。
4. 微变只承担“避免大量同脸”的职责，不应破坏第一层势力识别和第二层身份轮廓。
5. 核心 50 人的全参数定制优先于模板 seed；次要武将可在未来逐步晋升为人工定制。

“173 人”同样只是候选方案的分层设想，本轮不修改人物数据、规模真源或现有头像配置。

## 五、未来启动前必须完成的审计确认

以下三项是**未来启动时的强制前置检查清单，不是本轮审计任务**。

### 1. 色板冲突排查

方案提出的势力配色（魏玄蓝／蜀翠绿／吴朱红／群赭金）尚未经过 `docs/design/ArtDirection.md` 视觉真源校验。启动前必须确认这些颜色是否与已经建立的语义色规则（军＝朱／政＝金／人＝宣／谍＝青）兼容，不能凭空引入新色值，避免重蹈“色板三分裂”覆辙。

### 2. 现有 SVG 参数体系现状确认

启动前必须审计当前 `ExpressionPortrait` / `OfficerPortrait` 实际的 face、crown、beard 参数结构和变体数量，确认本提案中的 `faceShape`、`bodyWidth` 等新增维度如何与现有参数体系整合。禁止未经审计另起一套并行参数体系。

### 3. 战场渲染系统现状确认

本方案相关构想还包含“兵牌系统”（战场地图单位表示）。启动前必须审计现有 S10 六角战斗、白刃战、单挑界面的实际渲染方式，确认是否已经存在相同或相近机制，并明确头像体系与战场单位表示的职责边界，避免重复实现。
