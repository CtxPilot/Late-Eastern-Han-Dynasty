# Session 190：大地图行政界面 UI 布局与信息架构审查

> 范围：大地图左栏/右栏政务菜单及其子面板。  
> 方法：对照 `07-ui-design.md` §5、§8、§11.1.4、§12、§13.4，检查当前 React 组件，
> 并在 1440×900 Headless Chrome 中实际进入刘备军与董卓政权，逐项展开取证。  
> 本报告只提出信息架构与交互建议，不评价色板，也不改代码。

## 一、结论

**建议现在迁移到 `07-ui-design.md` §12 已拍板的“底部命令坞 + 侧边参数抽屉 + 居中终审窗”架构，
停止继续给左栏手风琴增加功能。**

不建议一次性重写全部界面。应采用“先搭壳、再按类别迁移”的渐进式替换：先建立九分类命令坞、
抽屉容器和统一终审窗，再依次迁移朝廷/人事/外交等压力最高的域，旧手风琴只在迁移期作为兼容入口，
每迁完一类就删除对应旧入口。

原因不是未来可能出现容量问题，而是当前已经同时出现：

1. 现行一级分类与 §12 的正式九分类不一致；
2. “人事”已成为四种工作流纵向拼接的长面板；
3. “君主”同时承担人物状态、政治阶段、战略能力和回合推进；
4. 多个状态变更操作绕过 §12.4 强制终审；
5. “结束回合”已存在两个入口，且两者都可单击立即推进；
6. HC-P1/P2 与城市设施继续接入后，旧结构没有稳定的归属规则和容量上限。

## 二、当前架构事实

### 2.1 分组依据

左栏当前顺序为：

`战役 → 谍报 → 计谋 → 总军师 → 家族 → 人事 → 外交 → 君主 → 己方城池`

它不是单一维度的分类：

- “战役/谍报/计谋/家族/人事/外交”按功能领域；
- “总军师”按角色/岗位；
- “君主”按角色，但内部又放势力阶段能力与结束回合；
- “己方城池”是导航快捷列表；
- 内政与部分军事则按“当前选中城市”放在右栏。

因此它实质上是开发历史形成的混合导航，而不是新玩家可推导的任务分类。老玩家可以靠记忆使用，
新玩家无法从同一规则判断“任命总军师”“霸府官职”“伪诏宣战”“出征”分别应去哪。

### 2.2 展开与容量

- 左栏共 9 个一级折叠项，且一次只能展开一个。
- 右栏共 6 个一级折叠项，也一次只能展开一个。
- 左栏固定宽 240px；右栏约 288px；复杂表单被压在窄栏内。
- “人事”展开后依次拼接：武将名册、搜索与登用、任命、美女资源。实测在 900px 高度下，
  仅名册就占据大部分视口，后三段必须在面板内部长距离滚动才能发现。
- “外交”按目标势力重复铺设四按钮；势力扩容后面板高度随势力数线性增长。
- “君主”在开府后按所有存活目标逐条铺设“伪诏宣战”，同样随势力数线性增长。

武将详情的四页签（属性/家族/装备/列传）证明了“复杂对象信息分面”的模式有效，但不能机械地给每个
手风琴再套一层页签。应把这个范式提升为：**一级按任务域导航，抽屉内按同一对象/同一工作流分栏或页签**。

## 三、问题清单

### P0 — 必须改

#### P0-1：战略性状态变更没有统一终审

Headless 实测“开霸府”点击即提交；代码中“伪诏宣战”同样直接调用 API。外交进贡、献美、点化、
结盟以及右栏内政/征兵/训练/出征也多为直接提交。

这与 §12.4“所有改变状态或推进时间的命令必须经过终审”的规则冲突。尤其开府、伪诏宣战属于
低频高影响/不可轻易撤销的战略决策，应显眼但不可误触；目前只满足“入口可见”，不满足“防误触”。

**建议**：迁移第一批先覆盖开府、伪诏宣战、普通宣战/结盟和结束本月。危险操作使用深红终审，
明确列出目标、消耗、冷却、声望影响和不可逆后果。

#### P0-2：“结束回合”重复入口且行为违反 §12.5

TopBar 有常驻“结束回合”，君主折叠内又有一个“结束回合”。两者触发同一动作，形成明确重复入口；
同时都没有“结束本月”汇总终审。

**建议**：保留 TopBar/未来底部命令坞中的唯一常驻“进行”入口，删除君主内重复项；接入 §12.5
月度汇总确认。这样高频操作仍保持 1 次打开 + 1 次确认，不会被藏入折叠项。

#### P0-3：现行分类与已批准的正式分类持续分叉

§12 正式分类是：

`内政｜军事｜人事｜外交｜计略｜情报｜屯田｜家族｜朝廷`

当前却把内政/军事分散到右栏，把总军师提升为一级，把君主与朝廷概念混用，并另设战役和城池快捷项。
继续在旧分类上接 HC-P1/P2，会造成同一规则在设计和代码中拥有两套入口归属。

**建议**：立即冻结旧一级菜单新增。新政治阶段能力统一按 §12 进入“朝廷”；总军师任免进入
“朝廷”，态势/献策进入“计略”；城池列表归导航/对象选择，不作为命令类别。

#### P0-4：君主折叠项已过载且扩展方向错误

当前君主项包括君主姓名/政治头衔、开府资格或失败原因、皇权和冷却、对每个势力的伪诏按钮、
结束回合。霸府官职又实际位于“人事 → 任命”，并非全部 HC-P0 内容都在君主项内。

HC-P1/P2 若继续加入称王、称帝、国号、迁都、封爵、诏令与更多政治资源，线性按钮列表必然失控。

**建议**：将其升级为“朝廷”域，而非继续拆成更多左栏手风琴：

- 概览：政治阶段、正统/皇权、威望、国库和冷却；
- 爵位与官制：霸府/王国/帝国官职总览和任命入口；
- 诏令与外交：伪诏、奉迎、封赏等；
- 国策与制度：长期政策、技艺、文化；
- 大事：开府、称王、称帝、迁都，统一危险终审。

### P1 — 强烈建议

#### P1-1：人事面板应从纵向拼盘改为任务分栏

“武将名册 + 搜索登用 + 任命 + 美女赏赐”虽都与人员有关，但使用频率、对象和完成路径不同。
当前把四块顺序堆叠，造成发现性依赖滚动位置。

**建议**：人事抽屉采用页签/分栏：

- 名册：浏览、筛选、武将详情；
- 招贤：搜索、登用、俘虏录用；
- 调动：移动、编入/召回军队（未来）；
- 任官：文官/地方官/军职/霸府官职；
- 赏罚：赏金、宝物、美人、没收。

复用 OfficerDetail 的页签范式，但页签围绕人事任务，不把不同对象的完整表单同时展开。

#### P1-2：外交应先选势力，再看关系与动作

当前每个势力卡片平铺“进贡/献美/点化/结盟”，既重复按钮，也无法容纳未来停战、宣战、求援、
借道、联姻、领土交换等动作。目标势力越多，扫描成本越高。

**建议**：外交抽屉左侧为可搜索/排序的势力列表，右侧（或第二步）为选中势力的关系概览、
条约、使节行动和战争行动页签。伪诏宣战可在“朝廷 → 诏令”发起，但目标选择与外交势力选择器复用，
不要再铺一套目标按钮。

#### P1-3：出征入口语义分裂

左栏“战役”负责 Army 编成/行军，右栏“军事操作”又提供“出征攻城”，页面另有“进入南郡战场”。
这些不完全是同一操作，但用户看到的都是“发动军事行动”，当前缺少明确的层级说明。

**建议**：统一到“军事”域：

- 出征：选起点、目标、编成；
- 军团：进行中 Army 与补给；
- 战场：可进入的郡域/交战实例；
- 城防：征兵、训练、驻军和设施。

地图右键/城池详情可保留上下文快捷入口，但必须打开同一军事命令草稿，而非维护第二套提交逻辑。

#### P1-4：禁用原因规范执行不一致

HC-P0 伪诏按钮同时在正文与 `title` 显示原因，做得正确；但大量其他禁用按钮仅依赖 `title`，
触屏不可见，且有些按钮的提示是固定成本文案，不一定解释当前为何不可用。

**建议**：统一为按钮邻近的可见原因/状态行；`title` 只作补充。抽屉底部固定显示当前命令的门禁清单，
不要让玩家逐个悬停猜原因。

#### P1-5：右栏应从“第二套主菜单”退回对象详情

右栏的“基本信息/人口/粮耗/内政/军事/日志”混合只读数据与命令入口。城市设施扩展后继续增加折叠项，
会与左栏同样失控。

**建议**：右栏保留城市对象摘要和页签（概览/人口/设施/驻军/日志）；状态变更动作通过上下文按钮
打开底部对应类别的命令抽屉。这样城市详情负责“看”，命令系统负责“做”。

### P2 — 优化项

#### P2-1：建立收藏/最近使用，而不是用重复入口解决高频

老玩家需要速度，但不应复制提交逻辑。命令坞可提供最近命令、快捷键或收藏位；所有快捷入口都创建
同一命令草稿并进入同一终审。

#### P2-2：一级入口应有状态徽章

战役可显示进行中军团数，情报显示到期/告警数，外交显示待答复数，朝廷显示可决大事或冷却完成。
目前少量 badge 只显示军团数、家族人数、美女库存、城市数，语义不统一。

#### P2-3：把导航、对象详情、命令三类交互明确分层

- 导航：地图、己方城池、Army、人物搜索；
- 对象详情：城市/武将/势力/军团的只读与局部状态；
- 命令：九分类命令坞、参数抽屉、统一终审。

当前“己方城池”与命令并列，是三类职责混合的典型表现。

## 四、常用操作可达性

| 操作 | 当前路径 | 评价 | 建议目标 |
|---|---:|---|---|
| 结束回合 | TopBar 1 次；君主折叠 2 次 | 短，但重复且易误触 | 常驻“进行”→终审，共 2 步 |
| 城市日常内政 | 选城→右栏折叠→按钮，通常 2～3 步 | 尚可，但操作与详情混合 | 选城→上下文快捷命令→终审 |
| 简化出征攻城 | 选目标城→军事操作→出征，约 3 步 | 路径短，语义与战役编成分裂 | 统一军事草稿；地图可快捷打开 |
| 战役编成 | 战役→选择多项→提交 | 窄栏承载复杂表单，空间不足 | 军事抽屉/大面板 |
| 开霸府 | 君主→开霸府，2 步 | 容易发现但无防误触 | 朝廷大事→信息完整的终审 |
| 伪诏宣战 | 君主→目标按钮，2 步 | 显眼但目标线性铺开、无终审 | 朝廷诏令→选目标→危险终审 |
| 霸府官职任命 | 人事→向下滚到任命→选人/职位 | 归类可辩护，但发现性差 | 人事·任官；朝廷概览提供同源跳转 |

## 五、迁移工作量

判断为 **中大型前端重构，非服务端玩法重写**。

建议拆成 4 个可独立验收的切片，约 **4～6 个常规 Session**；若同时补齐所有现有状态变更命令的终审
与 Headless 全流程回归，按 **6～9 个 Session** 预估更稳妥：

1. **壳层（1～2 Session）**：九分类底部命令坞、抽屉状态机、响应式布局、统一命令草稿接口；
2. **安全闭环（1～2 Session）**：统一终审窗，先迁“结束本月/开府/伪诏/外交重大动作”；
3. **高压域（2～3 Session）**：人事、外交、朝廷迁移，建立共享对象选择器；
4. **其余域与清理（2 Session 左右）**：军事/计略/情报/家族/内政，移除旧入口，补快捷键和回归。

服务端 API 与已有引擎大多可复用。主要成本在前端状态管理、命令描述模型、草稿保留、统一门禁文案、
终审字段适配，以及逐条浏览器回归。不要把工作量误判成单纯 CSS 换布局。

## 七、决策建议

本次建议可直接拍板为：

> **现在开始渐进迁移；旧手风琴冻结新增，不做一次性大爆改。**

HC-P1 开工前至少应先完成“命令坞壳层 + 朝廷抽屉 + 统一终审”的第一阶段，否则称王/称帝功能会继续
把临时信息架构固化，之后迁移成本只会更高。
