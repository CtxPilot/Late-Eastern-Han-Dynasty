# Session 200：英雄集结完整展示性流程排查

> 范围：选剧本 → 城市信息/内政 → 人事 → 出征/战斗 → 外交 → 谍报/计谋 →
> 连续 8 回合 → 朝廷/霸府。  
> 方法：1440×900 Headless Chrome，从开卷页开始实际点击；选用 **曹操军**，因其开局
> 17 城、同时与刘备敌对、孙权中立、吕布交战，并控制洛阳汉帝。页面状态与
> `/api/game/state` 权威快照交叉核对。  
> 结论性质：本轮只排查、截图和定位，不修改任何功能代码。

## 一、结论

**英雄集结的核心展示链路可以完整走通，未复现 190 剧本曾出现的外交误判野战、Army ID
复制或结盟禁用失效；但发现 1 项明显异常、3 项体验/覆盖问题。**

本次实际从 190 年 1 月推进到 190 年 9 月：

- 17 城大地图、10 名玩家在职武将名册、3 个外交目标均正常渲染，未见白屏、虚拟滚动异常
  或明显卡顿；
- 五项内政、搜索、三名武将详情、进贡、结盟、密探、离间计均可实际完成；
- 曹仁军对 `war` 的吕布军平原正常围城并强攻占领，Army ID 全程唯一；
- 夏侯惇军出发后，曹操—刘备关系变为 `friendly`；抵达汉中时未触发野战，后续转为
  `garrison`；
- 连续回合中吕布 AI 实际出征并攻占剧县；三方 AI 每回合都有经营记录；
- 新朝廷抽屉是唯一朝廷入口，曹操可从该入口完成开霸府；
- 持续 Chrome 监听仅收到 Vite、React DevTools 与字体加载信息，**控制台 error/exception 为 0**。

问题统计：**阻塞性 0 项、明显异常 1 项、体验瑕疵 3 项**。

需要特别澄清：当前“英雄集结”是 **0-A Demo**。它是曹操 17 城开局，但运行时总计仍只有
4 势力、30 武将；玩家在迷雾下可见 10 名本势力武将，外交面板只有 3 个目标。因此本轮验证了
“多城”，但没有真正覆盖 0-B 级别的“大量势力/大量武将外交列表”压力。

## 三、问题清单

### 明显异常 A-1：出征目标按“任意己方前线”聚合，未按当前出发城过滤

**复现**

1. 英雄集结选择曹操，当前城为洛阳。
2. 展开战役，选择曹操为主将。
3. 目标下拉可选择下邳。
4. 点击出征，终审正常显示“洛阳→下邳”且允许确认。
5. 确认后才提示“洛阳 与 下邳 无官道直达（战役层首跳须邻接）”，终审停留。

**影响**

- 17 城势力的目标下拉汇总了所有前线方向，玩家无法判断哪个目标属于当前出发城；
- 城越多，错误候选越多，属于只在多城开局中显著放大的问题；
- 与“统一终审提交前再校验”不冲突：服务端拒绝是正确的，但参数抽屉本应避免提供必定非法的候选。

**定位**

- `client/src/components/campaign/CampaignPanel.tsx:78-101`：`enemyCities` 遍历所有己方城市，
  聚合其全部邻接敌城；
- `CampaignPanel.tsx:245-255`：当前出发城仍直接渲染上述全局集合；
- `server/src/engine/campaign.ts:151-153`：服务端按真实 `fromNodeId` 正确拒绝。

**证据**

- `14-campaign-enemy-review.png`
- `15-campaign-enemy-marching.png`（文件名保留操作时命名；截图实际是提交被拒状态）

### 体验瑕疵 U-1：友好势力城内的军队被标为“驻守”，语义容易误解

夏侯惇军抵达刘备控制的汉中后正确地没有发生野战，但下一回合转为 `garrison`，UI 显示
“驻守 · 汉中”。城池仍属刘备，权威 `CampaignNode.ruler=2`，所以没有发生偷占；但“驻守”
通常暗示本方控制或受邀驻军，当前没有“借道/友军共处/待命”区分，也没有说明如何继续行动。

这是表现与状态语义问题，不是 190 修复回归：外交过滤本身工作正常。

**涉及**

- `server/src/engine/campaign.ts:399-414`：非敌对目标统一转 `garrison` 并记“驻守待命”；
- `client/src/components/campaign/CampaignPanel.tsx`：统一把 `garrison` 显示为“驻守”。

### 体验瑕疵 U-2：AI 反馈混有“占位经营”，无法从 UI 判断三方决策质量

8 回合内三方每月均产生 `ai_placeholder`：“经营了 N 座城（Demo AI）”；吕布另有真实军事
出征/攻占，三方也会发起计谋、谍报与寻访。系统稳定，但“多个 AI 都有合理决策产出”目前只能
确认它们都被调度，不能据此证明刘备、孙权的军事决策质量。

这是已知 Demo 成熟度边界，不是新崩溃；大规模正式验证应在 AI 内政占位替换后重做。

### 体验瑕疵 U-3：同一条计谋结算文案出现“失败；成功”的自相矛盾组合

190-09 的权威日志出现：

`【计谋】离间计失败；离间计成功：刘备军 与 曹操军 友好 −18`

当月存在多方多条离间计，数值状态本身可解释为不同计谋分别失败/成功，但合并为一条日志后没有
施计者或分隔对象，玩家会理解为同一计谋同时失败和成功。此类多势力并发结算在 190 小剧本流程
中未被观察到，是本次复杂网络下的新体验问题。

**涉及**：回合计谋批量结算与 `actionLog` 汇总（`server/src/engine/plot.ts` /
`server/src/engine/turn.ts`）。

## 四、190 修复项复验结论

| 既有修复 | 英雄集结复验 | 结论 |
|---|---|---|
| 外交误判野战 | 夏侯惇军到达 `friendly` 的刘备汉中，连续 7 回合未交战 | **通过**；仅有 U-1 状态文案问题 |
| Army ID 复制 | 玩家两军 + 吕布 AI 军，多回合与一次玩家强攻、一次 AI 攻城后逐回合检查 ID | **通过**；重复 ID 始终 0，控制台无 React key 错误 |
| 结盟按钮禁用 | 刘备 -30、孙权 0、吕布 war 均禁用且附具体原因；孙权到 30 后才启用 | **通过**；终审 64%，成功后改 allied |

未发现新的外交敌我判定或 Army 回写边界漏洞。

## 五、性能与稳定性观察

- 当前权威切片：30 城、4 势力、30 武将；曹操开局 17 城，玩家迷雾快照可见 10 将；
- 10 人名册直接渲染正常，没有足够数据触发虚拟列表压力；
- 外交面板仅 3 个目标，不构成大列表压力测试；
- 连续回合稳定阶段约 0.36 秒/次（Headless、同机开发模式，仅作相对观察）；
- 8 回合后玩家可见 CampaignArmy 3 支，重复 ID 0；
- 控制台 error/exception 0；未见后端断连、空白页或操作后状态不刷新。

因此，“17 城多城状态稳定”可以判为通过；“大量势力/大量武将渲染性能”因当前数据切片规模
不足，**不能宣称已验证**。

## 六、建议处理顺序

1. 优先修 A-1：目标下拉按 `selectedCityId` 对应节点的 `adjacentNodeIds` 过滤，并在终审前置
   再校验中给出相同原因。
2. 为非敌对外国城增加“友军待命/借道”状态文案，或明确复用 `garrison` 的设计语义。
3. 计谋批量日志逐条带施计者、目标和结果，不把不同计谋压成一条矛盾句。
4. 真正的外交/名册规模压力测试留到 0-B 或新增更多势力的专用性能夹具，不应以当前 4 势力
   英雄集结替代。
