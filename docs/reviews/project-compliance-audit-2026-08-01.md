## 3. 风险等级

| 等级 | 定义 | 发布处理 |
|---|---|---|
| 严重 | 可导致现实人身伤害、重大违法或立即失陷 | 立即停止相关功能/分发 |
| 高 | 权属不明、未成年人风险、完整隐私记录或部署后可被直接滥用 | 发布前必须关闭 |
| 中 | 条件性风险、合规资料缺失、纵深防御不足 | 限期整改并设发布条件 |
| 低 | 治理、可追溯性或一致性缺口 | 纳入常规修复 |

本次未判定“严重”项。

服务端只检查阵营、婚姻状态和配偶，不检查 `currentYear - birthYear`；客户端候选列表也只检查婚姻状态。0-A 数据中孙尚香生于 189 年、初始单身且属于势力 3；在 190 年剧本中年龄约 1 岁，仍可能成为婚配候选。`giftBeauty` 同样缺少年龄约束。这是可由数据和代码直接复现的未成年人保护缺陷。

**整改**

1. 立即在服务端唯一真源增加成年门槛和 `appearYear`/可用状态约束；客户端只做镜像提示，不代替服务端校验。
2. 禁止任何未成年角色进入婚配、随侍、赠与、后宫或具有性/亲密关系含义的流程。
3. 对全部剧本年份×女性角色执行属性测试；为 189 年出生/190 年场景加入明确拒绝测试。
4. 审核历史婚姻资料时区分史实记录与玩家可执行机制，并添加内容说明。

**验收**：API 直接调用、UI 和存档恢复三条路径均拒绝未成年角色，边界年龄前后均有测试。

### ETH-02｜具名女性被作为忠诚资源转移｜高

**位置**

- `server/src/engine/personnel.ts:454-520`
- `server/src/routes/game.ts:152-162`
- `client/src/services/api.ts:187-194`
- `client/src/stores/gameStore.ts:508-514`
- 历史字段/文案：`beauties`、`赏赐美人`、`献美`

**证据与评估**

系统把具名女性角色挂入武将 `beauties` 列表、允许转移，并以金钱换取忠诚增益。这与 S09 已确定的“宫廷人脉”非人格资源方向不一致，也把人物当作可交易奖励。和 ETH-01 组合时风险进一步上升。

**整改**：废弃具名女性转移 API 和字段；将外交/忠诚效果迁移为“宫廷人脉、家族联姻谈判、举荐、宴飨”等非人格化机制；历史人物保留自主身份、关系状态和拒绝/同意条件。为旧存档提供单向迁移，不保留可赠与语义。

### ETH-03｜历史族群称谓和战争内容缺少统一提示｜中

**位置**：女性/武将描述、战斗与事件文本，例如 `server/src/scripts/generate-0a-data.ts:797`

**证据与评估**

项目包含死亡、俘虏、瘟疫、间谍、赌博及《三国演义》来源的“南蛮”等历史称谓。其存在本身不等于违法或不当，但如果界面不区分史书、演义和现代设计措辞，可能把带时代偏见的称谓作为当代客观分类。

**整改**：增加内容提示和来源层标签；叙事引用可保留原词并说明语境，系统分类和现代旁白使用中性称谓；建立本地化敏感词人工复核表。

### SEC-01｜无认证、全开放 CORS 的全局状态变更接口｜高（部署条件性）

**位置**

- `server/src/app.ts:8-15`
- `server/src/index.ts:13-39`
- `server/src/routes/game.ts`

**证据与评估**

`cors()` 接受任意来源，HTTP API 和 `/ws` 无认证；大量 POST 路由可改变单例 `currentGame`。`server.listen(PORT)` 未显式限制回环地址，实际绑定行为不应依据日志中的 `localhost` 文案判断。纯单用户本地 Demo 下影响较低；一旦端口被局域网、容器或公网暴露，任意网页或客户端都可能读写游戏状态、触发高成本操作或干扰其他用户。

**整改**

1. 开发默认显式绑定 `127.0.0.1`；拒绝非白名单 Origin。
2. 若支持远程访问，增加会话认证、授权、CSRF 防护和每局隔离；WebSocket 在升级时校验会话与 Origin。
3. 所有状态变更使用 Zod 请求模式，不用 `Number(req.body...)` 作为唯一校验；加幂等/并发版本控制。
4. 增加速率限制、请求体上限、安全响应头、审计日志和反向代理 TLS 指南。

**验收**：跨源网页、未认证 HTTP、未认证 WebSocket、重放和并发冲突测试均按部署模型被拒绝。

### SEC-02｜缺少纵深防御与部署安全基线｜中

**位置**：`server/src/app.ts`、`SECURITY.md`

**证据与评估**

未发现 `helmet`、速率限制、显式 JSON 大小策略、生产部署边界或安全头配置；SECURITY 只说明私下报告漏洞，没有威胁模型、支持渠道和响应时限。当前 React 源码未发现 `dangerouslySetInnerHTML`、`eval` 或 `new Function`，可降低部分 XSS 风险，但不能替代服务端控制。

**整改**：形成本机 Demo/局域网/公网三档部署配置；默认拒绝式 CORS、CSP/安全头、body 限额、限速和结构化错误；补安全报告联系方式及 SLA。

### SEC-03｜依赖当前无已知漏洞，但缺持续供应链门禁｜中

**位置**：`package.json`、`pnpm-lock.yaml`、GitHub Actions

**证据与评估**

审查时 `pnpm audit --json` 返回 0 个已知漏洞；这只是时间点结果，不证明未来安全。项目也没有生成 SBOM、依赖来源签名/哈希策略或许可证变化门禁。

**整改**：CI 固定执行冻结锁文件安装、漏洞审计、许可证差异检查和 CycloneDX/SPDX SBOM；高风险升级人工审批；保存每次发布的审计结果。

## 7. 建议新增的自动化门禁

1. **资产门禁**：新增 PNG/字体/音频时，清单缺任一字段即失败；截图递归登记嵌入资产。
2. **许可证门禁**：锁文件许可证集合发生变化时生成差异；禁止未知、无许可和未审批的强 copyleft/非商用条目进入发布物。
3. **秘密/PII 门禁**：扫描当前提交和完整待推送范围；日志、数据库、会话文件名直接阻断。
4. **安全门禁**：依赖审计、Zod 路由覆盖、跨源/未认证集成测试、WebSocket Origin 测试。
5. **伦理门禁**：所有亲密关系、婚姻、赠与相关动作执行成年和可出现状态属性测试。
6. **来源门禁**：代码评审模板要求声明“原创/第三方/生成式/clean-room”及证据链接。

## 9. 最终结论

项目当前具有较好的原创开发规则、MIT 许可基础和公有领域底图选择，但执行层仍存在“规则已写、资产和旧玩法未完全收口”的落差。版权侧最急迫的是四张无权属链 PNG 和外部 Demo 污染路径；敏感内容侧最急迫的是未成年校验和具名女性资源化；隐私与安全侧最急迫的是完整 Agent 数据库的本地暴露及无认证服务的部署边界。

在 P0 五项关闭并完成复验前，结论为：**允许继续受控本地开发，不建议公开发布素材包，不建议部署可被其他设备访问的服务。**
